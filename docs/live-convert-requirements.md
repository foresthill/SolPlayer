# ライブ変換（タブ音声キャプチャ→リアルタイム周波数変換）要件整理

> このドキュメントは、機能の再設計・ブラッシュアップを（別のAIや人も含めて）
> 検討するための自己完結の要件整理です。前提知識なしで読めるように書いています。

## 1. プロダクト背景

**SolPlayer** はリアルタイム周波数変換付き音楽プレイヤー（Webアプリ、Next.js + Web Audio API）。
A=440Hzの音源を432Hz/444Hz等へ変換して再生するのが核となる価値。

- 変換式は厳密式 `semitones = 12 × log2(target/base)`（432Hzなら−31.77セント）
- 変換エンジンは SoundTouchJS（WSOLA方式のタイムストレッチ/ピッチシフト。テンポ維持でピッチのみ変更可能）
- ローカル音声ファイルの432Hz再生は完成済み（品質良好）
- デプロイ先: https://sol-player-web.vercel.app/ （Vercel、静的サイト）

## 2. この機能のゴール

**「YouTubeで聴いている曲を、432Hz等に変換して聴きたい」**

YouTubeは音声データを直接渡さない（埋め込みプレイヤーはブラックボックス）ため、
通常の方法では変換できない。それをどう実現するかがこの機能の主題。

## 3. 現在の実装（動作確認済み）

### 方式: タブ音声のライブキャプチャ

```
別タブのYouTube → getDisplayMediaでタブ音声キャプチャ
  → ScriptProcessorでリングキューに取り込み
  → SoundTouch(SimpleFilter)でピッチのみ変換（テンポ1.0）
  → ScriptProcessorで出力 → GainNode → スピーカー
```

- 音声は**保存せずリアルタイム処理のみ**（ダウンロードではないため規約面で防御可能。
  外付けイコライザーを通して聴くのと同じ構造）
- `suppressLocalAudioPlayback: true` で元タブを自動消音（変換後の音だけが聴こえる）
- `echoCancellation / noiseSuppression / autoGainControl` は明示的に無効化
  （Chromeのデフォルト音声通話フィルタが音楽の持続成分を削り「スカスカ」になるため。修正済み）
- 入力ジッタ対策のプリバッファ約0.3秒＋出力バッファ8192サンプル（プチプチ対策済み）
- 周波数はアプリのチューニング設定と連動（再生中の変更も即反映）
- 実装: `packages/audio-core/src/live-converter.ts`（エンジン）/
  `apps/web/components/player/live-convert-panel.tsx`（UI）

### 現在のUX（ここが課題）

Web再生タブ（YouTube埋め込みカード）の下部に同居しており、フローは:

1. 「① この動画を別タブで開く」ボタン → YouTubeのwatchページが別タブで開く
2. アプリのタブに戻り「② そのタブをキャプチャして432Hzで聴く」
3. Chromeの共有ダイアログで「タブ」→ 該当タブを選び「タブの音声も共有する」にチェック

## 4. 技術的制約（これまでの検証で確定していること）

| 制約 | 理由 |
|---|---|
| 同一タブの埋め込みプレイヤーを直接キャプチャできない | タブキャプチャは自タブの全音声を拾うため、変換後の出力音を再キャプチャして無限ハウリングする |
| キャプチャ対象は「タブ」限定が実質必須 | `suppressLocalAudioPlayback`（元音の消音）はタブ共有時のみ有効。またmacOSのChromeはウィンドウ/画面共有で音声を取れない |
| 共有ダイアログでのタブ選択は省略できない | セキュリティ上、getDisplayMediaは必ずユーザーの明示的な選択を要求する（プログラムから対象タブを事前指定するAPIは存在しない） |
| スマホ（iOS/Android）では実現不可 | タブ音声キャプチャAPI自体が存在しない。ネイティブアプリでも、iOSはシステム音声を取れず、Androidの再生キャプチャはYouTubeが拒否設定＋いずれも元音を消せず二重再生になる |
| レイテンシは0.3〜0.5秒程度 | プリバッファ＋処理遅延。音楽鑑賞は問題ないが、映像との口パクは僅かにずれる（ピッチのみ変換なのでテンポ同期は保たれる） |

## 5. 検討済みで却下した代替案（再提案時は却下理由の突破が必要）

1. **サーバーでYouTube音声を取得して変換配信** — 実質ダウンロード再配信でYouTube利用規約違反（ダウンロード禁止条項）。ストアアプリの審査も通らない。**採用不可**
2. **ストリームURL直接抽出（NewPipe方式）** — 同上の規約違反。採用不可
3. **YouTube IFrame APIのplaybackRate** — テンポは変わるがピッチは変えられない（そもそもピッチ保存仕様）
4. **マイクでスピーカー音を拾って変換** — 音質劣悪＋原音と二重に聞こえ実用性なし
5. **自宅PCを変換ステーションにしてスマホへWebRTC配信** — 技術的には可能で規約面もタブキャプチャと同等。ただし「PCを常時起動」が必要でユーザー要件（スマホだけで完結）に合わず保留

## 6. 現在の課題（ブラッシュアップしたい点）

### A. UX/見せ方（ユーザーフィードバック）
- 埋め込みプレイヤーのカードの下に同居しているのが直感的でない。
  「これはこれで独立した機能」として割り切った見せ方にしたい
- 案: 専用タブ/専用モード化（例:「チューナーモード」「432Hzリスニングモード」として
  全画面の専用UIにする）、手順のウィザード化、前回動画のワンタップ再開 など

### B. 音質
- ノイズ抑制無効化とプリバッファで大幅改善済み
- 残る改善余地: ScriptProcessor（非推奨API・メインスレッド処理）→ **AudioWorklet化**
  （別スレッド処理でUI起因のグリッチを根絶。`@soundtouchjs/audio-worklet` という公式派生も存在）

### C. 対応環境
- PCのChrome/Edge限定。Safari/Firefox/スマホは非対応（制約表の通り）

## 7. ブレスト結果と検証状況（2026-08 更新）

### ✅ 検証済み: インジェクション型Chrome拡張（ブレイクスルー確定）

ブレストで最有力とされた「拡張機能でYouTubeプレイヤーに直接トグルを注入」を
プロトタイプ実装し（`apps/extension/`）、E2Eで実測検証済み。

- **`chrome.tabCapture` すら不要**。コンテンツスクリプトから
  `createMediaElementSource(video)` で`<video>`要素の音声出力を丸ごとWeb Audioへ
  付け替える方式（世のYouTube用イコライザ拡張と同じ確立された手法）
- これにより: 二重再生が構造的に不発生 / 共有ダイアログ不要 / タブ移動不要 /
  映像はそのまま / 特別なpermissionも不要
- **実測: 440Hz動画 → 432.00Hz / 444.01Hz 出力を確認**。バイパス復帰・再開も正常
- 残課題: プレイヤーバー内へのボタン注入（現在は右下浮遊ボタン）、
  AudioWorklet化、本体との設定連携、ストア配布
- 住み分け: Webアプリ＝ローカルファイル＋同期、拡張＝Webストリーミング変換

### 承認済みの改善方針（ブレストより）

- **AudioWorklet移行は必須**（ScriptProcessorはメインスレッド動作でUI描画と競合しグリッチ源）。
  まず既存JS実装のWorklet載せ替え → 限界を感じたらWASM化、の2段構え
- **Document Picture-in-Picture**: タブキャプチャ方式の弱点（映像が見えない）への対策。
  現在は取得直後に破棄しているキャプチャの映像トラックを、`<video>`やPiP小窓に
  表示する実装が可能（追加検証は容易）
- **エッジケースを制約に追加**（下記8参照）: DRM/CORS保護コンテンツは仕様により無音化
  （file://での無音化として実測確認済み。EME保護のYouTubeムービー等も同様の想定）。
  バックグラウンドタブのスロットリングによる音飛びリスク（AudioWorklet化で軽減）
